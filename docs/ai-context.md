# AI Context - Draive / Code Language
Updated: 2026-07-04

Read this first. Update it whenever semantics or process change.

## Strategic Direction (active)
- Web-first for code-first 2D interactive applications and games, while preserving native portability.
- Keep language-facing engine APIs backend-agnostic; host bindings provide platform-specific implementations.
- Generated apps use a worker-hosted Rust/Wasm bytecode-v12 VM; JavaScript owns scheduling and browser APIs and retains the reference VM for conformance.
- A typed direct-Wasm backend is available through hidden `--web-backend direct-wasm`. It emits `code-app.wasm` with native structured control flow and typed layouts; it is the active compiler/runtime focus, while the Rust/Wasm VM stays default until browser compatibility, memory behavior, bytecode-free host metadata, and full error/fuzz parity pass.
- Capability query + explicit fallback policy is a required design constraint for predictable cross-target behavior.
- Near-term product target: write Code source, build once, and get a deployable website.
- Default web runtime target: full-window browser app, centered `640x360` safe area with hybrid-expanded world framing, scene-object authoring, separate HUD space, a first wrapper layer in `lib/engine/`, and browser-backed drawing/image-sprite/keyboard/primary-pointer/audio/diagnostics support for V1.
- Notes-derived app direction: the first graphical app profile slice is now the public default for `.code` inputs, with top-level lifecycle authoring and usage-based implied engine imports across web-app modules; keep explicit `MainScene` valid and preserve a path to future native graphical targets.
- Public naming direction: use `PascalCase` for types/namespaces and `camelCase` for functions, methods, fields, locals, constants, lifecycle hooks, and collection methods. Avoid source-level `snake_case`; compact domain terms such as `rgb` / `rgba` are accepted when they are clearest.
- Process gate: every performance or feature pass ends by packaging, installing, and smoke-testing the current Windows Release compiler with `scripts/install-local.ps1`; use `-SkipTests` only when the full harness already passed during that pass. The installer auto-increments numeric prerelease versions when the installed compiler already matches the project version, ensures `$HOME/.code-language/bin` is on User PATH, and updates the current PowerShell session PATH when possible; use `-NoAutoIncrementVersion` to require a manual bump. Release packaging requires Rust 1.83 with `wasm32-unknown-unknown`; full test validation also requires the Windows MSVC linker for Rust host tests. `scripts/release.ps1` preflights Rust/Wasm tooling, auto-loads Visual Studio Build Tools through `vcvars64.bat` when `link.exe` is not on PATH, and runs `cargo test --locked` for `runtime-wasm` only when tests are enabled.

## Current Capability Snapshot
- Types: integer/whole/real, sized numeric boundary types (`integer8`, `integer16`, `integer32`, `whole8`, `whole16`, `whole32`, `real32`, `real64`, with `byte` exactly aliasing `whole8` and `real64` exactly aliasing `real`), boolean, string, enums (`enum Name { Member; Other = 5; }` with `Enum.Member` access and strong enum-to-enum typing), records (`record Name { ... }` with constructors, field access, and copy-on-assignment/pass/return semantics), array<T> (literals `{...}`, `new array<T>(n)`, `.length`, indexing, mutation, `append`, `removeAt`, preserved element typing through indexing/foreach), built-in collections (`map<Key, Value>`, `set<Value>`, `queue<Value>`, `stack<Value>` with shared `.length` and collection-specific methods), optional<T> as `T` or `none` with `== none` / `!= none` checks, direct unwrap in `T` contexts, and compatibility helpers (`.hasValue`, `.value`, `.or(fallback)`), `fallible<Value, ErrorCode>` and `fallible<Value>` for recoverable errors, same-module globals/constants, typed/void functions, and object types.
- Compiler type model: AST/parser/type-checker use `TypeRef`; named object types resolve via object symbol tables (fields + constructors + forward refs).
- Object rules: fields may use declaration defaults (`Type name = expression;`) or constructor assignment; fields without defaults require definite constructor initialization; defaults run per instance before constructor bodies and may read same-module globals / built-in constants but cannot read constructor parameters, `this`, sibling fields, or implicit fields. Constructor/method overloads resolve by typed signature (best-match conversions), methods lower to hidden static call targets with implicit `this`, object bodies support implicit field access / implicit `this` method calls when names are not shadowed by locals or parameters, object methods support implicit-void authoring, and functions/methods/constructors support trailing default parameters; reserved field names are `length`, `hasValue`, `value`, `or`.
- Constructor ergonomics: object/record primary constructors lower to normal constructors assigning same-named fields, records without explicit constructors get implicit field-order constructors for non-defaulted fields, and `TypeName(args...)` is shorthand for construction when normal function resolution does not apply. `TypeName.method(...)` is intentionally not construction sugar; use `TypeName().method(...)`.
- Record rules: records support fields, implicit/explicit constructors, methods, inline/external interface implementations, structural equality for hashable records, and use as `map` keys / `set` elements when hashable; all fields participate in equality/hash by default; contextual non-reserved `key` fields select the identity fields and `ignore key` excludes fields; collections are structural hash participants when their contained types are hashable; map/set insertion snapshots keys/elements; record methods clone `this` at method entry, so persistent updates use return-and-reassign.
- Interfaces: `interface Name { Type field; function<...> method(...); }` supports field and method requirements. Conformance remains explicit through empty data-only `implement Interface for Type {}` blocks, external method mappings, or inline object-body implementations `implement Interface.method(...) { ... }`. Interface-typed locals/params/returns/fields/arrays support runtime method dispatch and read/write access to declared interface fields.
- Control flow: if/then[/else], switch (no fallthrough), while, for, foreach (numeric or array), break/continue, return (implicit 0).
- Expressions: arithmetic (including `%` and truncating integral `/`), comparisons, logical and/or/not (short-circuit), assignment (including `+=`, `-=`, `*=`, `/=`, `%=` and postfix `++`/`--` across variables, object fields, array elements, map elements, and mutable same-module globals), function calls, integer literals with decimal/binary/octal/hex prefixes through the implemented `integer32` / `whole32` boundary range, decimal real literals (`1.5`, `1.`, `.5`), built-in real constants `pi` and `tau`, explicit numeric casts including sized numeric casts, enum-to-integer casts, integer-to-enum casts with literal validation, full-expression string interpolation/concat, and escaped literal interpolation braces with `\{` / `\}`. Bare-name resolution is locals/parameters, implicit `this` fields, same-module globals, then built-in constants. Use a `real` operand such as `1. / 2` or `1 as real / 2` for real division. Dynamic narrowing to sized numerics requires an explicit cast; sized stores and sized compound assignments are range-checked. Direct missing map reads still error, but map compound assignment on a missing key defaults the old value before storing.
- Time and math intrinsics: `unixMilliseconds()`, `unixMicroseconds()`, `monotonicNanoseconds()`, `monotonicTicks()`, `monotonicTicksPerSecond()`, `minimum()`, `maximum()`, `absolute()`, `sign()`, `lerp()`, `sine()`, `cosine()`, `squareRoot()`, `random()`, built-in constants `pi` and `tau`, plus native-only `sleepMilliseconds(integer)`.
- IO intrinsic: `readLine() -> string` (native-only).
- Host ABI baseline: compiler lowers print/time/math/native-only/engine intrinsic calls to `HOST_CALL` symbols; capability inference includes lowered host features such as `standard.input_output.read_line`, `std.time.sleep_ms`, `std.math`, and `engine.window/input/gfx/diagnostics/audio`; VM resolves via native/web host binding tables and throws target-aware `HostBindingError` on unsupported host calls.
- Engine ABI status: source-level prototype window-handle calls are `windowCreate`, `windowShouldClose`, `windowPresent`, `windowInputKeyDown`, `gfxClear`, and `gfxDrawRectangle`, while lower-level host ABI symbols may retain historical internal spellings. Scene-runtime source intrinsics `inputKeyDown`, `inputPointerWorldX`, `inputPointerWorldY`, `inputPointerScreenX`, `inputPointerScreenY`, `inputPointerIsDown`, `inputPointerWasPressed`, `inputPointerWasReleased`, `clear`, `drawRectangle`, `drawRectangleOutline`, `drawLine`, `drawCircle`, `drawCircleOutline`, `drawPolygon`, `drawPolygonOutline`, `drawText`, `drawImage`, `drawSprite`, `cameraView*`, `cameraSafe*`, `screenWidth`, `screenHeight`, `diagnosticsLast*`, and `audio*` now have browser-backed implementations for `vm-web`.
- Web app/runtime slice: public `compiler entry.code` emits a static site folder with `index.html`, a cacheable `code-runtime.wasm`, embedded bytecode, embedded Blob-worker source, a base64 Wasm fallback for direct-file execution, and copied assets. Generated apps use the Rust/Wasm VM in the worker with a main-thread Canvas/audio/input bridge, fixed 60 Hz updates by default, asynchronous profiling, and the existing scene/engine APIs.
- Engine wrapper layer: root `lib/engine/` currently provides canonical `engine.colors`, `engine.drawing`, `engine.input`, `engine.viewport`, `engine.diagnostics`, `engine.runtime`, `engine.audio`, and `engine.scene` modules over the raw scene-runtime helpers, with `engine.view` and `engine.loop` retained as compatibility re-exports.
- Scene composition: canonical `engine.scene` now provides explicit child-object registration through `Startable`, `Updatable`, `WorldDrawable`, `HudDrawable`, `Scene`, and `SceneLoop`; compatibility module `engine.loop` remains as a re-export while examples/docs migrate.
- Web harness: `web-runtime/` still contains a lower-level JavaScript bytecode runner + browser host binding table for raw `.bytecode` / `.codelib` loading; it is preview/bootstrap tooling, not the primary shipping workflow.
- Web app/runtime contract: `docs/web-app-v1.md` freezes the first implementation target around a scene object with `start/update/draw`, optional `drawHud`, full-window browser runtime ownership, centered `640x360` safe area, hybrid-expanded framing, and static-site output.
- Errors: `panic <expr>;` raises unrecoverable `UserError` with source file, line, column, phase, and call stack when bytecode debug metadata is available. Recoverable errors use `fallible<Value, ErrorCode>` or shorthand `fallible<Value>` (`integer` error code), `return error(code[, message]);`, `return error(message);` for integer-coded fallibles with code `0`, and `expr on error { ... yield fallback; }`; handler `error.code` has the declared enum/integer error-code type and `error.message` is a string. `fallible<void, E>` and propagation shorthand are deferred.
- Bytecode/VM: header v0x0C, spec v0.17; required `META` trailer contains pooled strings, source display paths, numeric host bindings, type/field layouts, record hash-field slots, and callable names/frame sizes. Debug entries include source IDs so runtime errors can report source file/line/column. The Rust/Wasm web VM predecodes numeric instructions and targets, uses contiguous stacks and 16-byte tagged values, stores fields in slots, and traces heap handles from VM roots.
- Modules/imports: recursive file-based module linking for `.code` files with top-level `public` / `package` / `private` visibility, member-level visibility for object/record fields/constructors/methods, legacy `export` compatibility, package-aware import checks, package declarations, grouped/selective imports, namespace imports, re-export imports, module-scope symbol conflict checks, import-chain diagnostics, alias imports for function/object/interface/enum exports, project/ancestor `lib/` search, and installed-compiler bundled `lib/` search.
- Package manifest/lockfile: nearest `code.package.json` is auto-discovered and schema-validated (v1 baseline) with compile-target gating (`targets`), validated `targetOverrides`, and host capability requirements (`hostAbi.requires`); local dependencies resolve and `code.lock.json` is emitted. `targetOverrides` are not yet used to auto-select a different compile entry.
- Library artifact: packages with `kind: "library"` emit `<package>-<version>-<target>.codelib` with embedded bytecode + metadata; resolver validates and prefers artifact paths in lockfile when present.
- Module tooling: `--dump-module-graph [outputPath]` emits entry/modules/import edges; supports text/json/dot output (via `--module-graph-format` or output extension inference); `--trace-linker` emits linker resolution steps.
- Targets/capabilities: public `--native` selects native compile/run; hidden maintainer `--target vm-native|vm-web` threads through module compilation; linker infers capability groups from package/import namespaces and rejects unsupported target capabilities (e.g., `std.fs` on `vm-web`).
- CLI flags: public `-o` / `--output`, `--native`, `--version`, `--help`; hidden maintainer/compat flags include `--run-tests`, `--skip-tests`, `--disasm`, `--dump-tokens`, `--out`, `--compile-only`, `--build-web`, `--emit-web-bytecode`, `--dump-module-graph`, `--module-graph-format`, `--trace-linker`, and `--target`.
- Editor support: `editor/textmate/code.tmLanguage.json` is the reusable lexical grammar for `.code` files; `editor/vscode` wraps it as the VS Code extension packaged by `scripts/package-editor-extension.ps1` into `code-language-vscode-<version>.vsix`. Windows installer scripts support opt-in `-InstallVsCodeExtension`; they never modify VS Code silently and print a manual command when `code` is unavailable.
- Direct backend validation uses `scripts/test-direct-wasm.mjs`, `scripts/benchmark-direct-wasm.mjs`, `CODE_WEB_BACKEND=direct-wasm` with the generated-worker browser suite, and `node scripts/test-browser-compat.mjs` for modern-browser compatibility.
- Direct-Wasm diagnostic builds may pass `--disable-garbage-collection`. The flag is valid only with `--web-backend direct-wasm`, records disabled-GC metadata in generated apps, and is allowed to leak memory.
- Tests: integration plus arithmetic/boolean/string/loop/panic fuzz. Runtime changes run `node scripts/test-web-vm.mjs`, `node scripts/test-rust-wasm.mjs`, `node scripts/test-generated-worker.mjs`, `node scripts/test-browser-compat.mjs`, and the relevant benchmark runners for C#/JavaScript/Rust-Wasm parity and browser validation.

## Not Implemented (yet)
- Language gaps: fallible-error propagation shorthand after the explicit `on error` model is exercised; exact `integer64` / `whole64`; numeric literal suffixes, exponent notation, semicolon injection, `fallible<void, E>`, and `foreach` over non-array collections. Planned map `foreach` should yield entry values.
- Stdlib/runtime gaps: broader standard-library surface beyond the current math/random and core container baseline.
- Engine/app ergonomics gaps: carry the implemented graphical app profile toward broader target-agnostic reuse; add byte-channel `rgba` on top of the implemented `byte` / `whole8` type surface; keep explicit `MainScene` valid.
- Dispatch/runtime polish: optimization beyond baseline interface dispatch tables.
- Module namespaces and stdlib versioning/layout.
- Constant pool, formatter/linter, REPL.
- Engine web runtime maturation: broaden the current `lib/engine/` wrapper layer beyond colors/drawing/input/viewport/diagnostics/audio, add advanced input/content handling and fuller audio mixing, and replace the remaining raw window-handle `engine.window`/`engine.input`/`engine.gfx` stubs with real browser-backed behavior or wrappers.
- Web runtime packaging stance: Rust/Wasm is mandatory for generated apps after clearing the parity and 1.5x adoption gates; `code-runtime.wasm` is a cacheable sidecar with an embedded direct-file fallback. The JavaScript VM is reference/test-only.
- GPU roadmap: `engine.gpu` ABI v1 + WebGPU backend (`vm-web`) + native GPU backend parity (`vm-native`).
- Capability query/fallback APIs for deterministic backend negotiation.

## Process Expectations
- When changing semantics: update spec, roadmap, bytecode spec (if opcodes), examples, tests. Run `--run-tests`.
- When making product-direction or workflow decisions: update the relevant docs in the same change. Do not let roadmap, README, and design docs drift.
- Keep examples status-labeled (`runnable`, `negative`, `planned`) and tested so stale draft files do not masquerade as working features.
- Prefer one example per capability cluster rather than one tiny file per minor feature.
- Preserve prior decisions; ask user when unclear.
- Prefer fully spelled-out user-facing names; avoid arbitrary abbreviations unless the term is a widely accepted domain term such as `hud`.
